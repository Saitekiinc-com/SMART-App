# 01_データベース詳細設計書

## 目的

データベース全体の設計方針と実装方針を記載する。
実装担当者が「迷わずにSQLを書き、テーブルを作成できる」レベルを目指す。

---

## 1. データベース選定理由

### 選定データベース

**PostgreSQL**

### 選定理由

| 項目 | 理由 |
|------|------|
| **技術スタックとの親和性** | 非機能要件定義書でPrisma ORM推奨。PrismaはPostgreSQLを主要サポートしており、型安全性とマイグレーション機能が充実している |
| **リレーショナルデータベースの要件** | ユーザー、チーム、ゴールなどのリレーショナルな関係を適切に管理できる |
| **ACID特性** | トランザクション処理が必要な操作（投票、招待受諾等）でデータ整合性を保証できる |
| **UUID型のネイティブサポート** | 主キーにUUIDを使用する設計に適している（`uuid`型が標準で利用可能） |
| **拡張性** | 将来的な機能拡張（全文検索、JSON型の活用等）に対応可能 |
| **オープンソース** | コスト面での優位性 |
| **コミュニティとドキュメント** | 豊富な情報とサポートが得られる |

## 2. スキーマ設計方針

### 基本方針

1. **正規化**: 第3正規形を基本とする
2. **中間テーブル**: 多対多の関係は中間テーブルで解決
   - `team_members`: users と teams の多対多
   - `votes`: users と smart_goals の多対多
3. **論理名と物理名の併記**: 設計書では論理名（日本語）と物理名（コード用）を併記
4. **主キー**: 全テーブルでUUIDを使用（`uuid`型）
5. **タイムスタンプ**: `created_at`, `updated_at` を標準化
6. **ソフトデリート**: 物理削除を基本とする（論理削除は不要）

### スキーマ構成

- **データベース名**: `saiteki`（開発環境）、`saiteki_production`（本番環境）
- **スキーマ名**: `public`（デフォルトスキーマを使用）
- **文字コード**: `UTF-8`
- **照合順序**: `C`（大文字小文字を区別）

## 3. 命名規則

### テーブル名・カラム名の命名規則

| 対象 | 規則 | 例 | 補足 |
|------|------|-----|------|
| **テーブル名** | スネークケース、複数形 | `users`, `team_members`, `smart_goals` | 中間テーブルも複数形（`team_members`, `votes`） |
| **カラム名** | スネークケース | `created_at`, `user_id`, `vote_count` | 単数形で記載 |
| **主キー** | `id` | `id` | 全テーブルで統一、UUID型 |
| **外部キー** | `{参照先テーブル名}_id` | `team_id`, `user_id`, `goal_id` | 参照先テーブルの単数形 + `_id` |
| **タイムスタンプ** | `created_at`, `updated_at` | `created_at`, `updated_at` | 作成日時・更新日時を標準化 |
| **フラグ** | 動詞の過去分詞または形容詞 | `used`, `completed`, `read` | boolean型で `DEFAULT false` |
| **カウント** | `{対象}_count` | `vote_count` | 集計値は `_count` サフィックス |
| **トークン** | `token` | `token` | ランダム文字列（UUID等） |
| **有効期限** | `expires_at` | `expires_at` | timestamp型 |
| **使用日時** | `used_at` | `used_at` | 使用済みフラグとセットで使用 |

### 制約名の命名規則

| 制約種別 | 規則 | 例 |
|----------|------|-----|
| **主キー** | `{テーブル名}_pkey` | `users_pkey`, `teams_pkey` |
| **外部キー** | `{テーブル名}_{カラム名}_fkey` | `teams_created_by_id_fkey`, `smart_goals_team_id_fkey` |
| **UNIQUE制約** | `{テーブル名}_{カラム名}_key` または `{テーブル名}_{カラム1}_{カラム2}_key` | `users_email_key`, `team_members_team_id_user_id_key` |
| **CHECK制約** | `{テーブル名}_{カラム名}_check` | `team_members_role_check` |

## 4. データ型選定方針

### PostgreSQLデータ型選定基準

| 用途 | PostgreSQL型 | 選定理由 | サイズ・制約 | 例 |
|------|---------------|----------|--------------|-----|
| **主キー** | `UUID` | 分散環境での一意性、セキュリティ（推測困難）、Prismaとの親和性 | - | `id UUID PRIMARY KEY` |
| **短い文字列（固定長想定）** | `VARCHAR(n)` | 長さ制限がある文字列。nは実際の最大長に合わせる | 例: `VARCHAR(50)`, `VARCHAR(100)`, `VARCHAR(255)` | `name VARCHAR(100)`, `email VARCHAR(255)` |
| **長い文字列（可変長）** | `TEXT` | 長さが可変の文字列。制限なし（実質最大1GB） | - | `specific TEXT`, `message TEXT` |
| **整数** | `INTEGER` | 数値計算が必要な場合。符号付き32bit整数 | -2,147,483,648 〜 2,147,483,647 | `vote_count INTEGER`, `sort_order INTEGER` |
| **真偽値** | `BOOLEAN` | フラグ値。true/false | `true`, `false`, `NULL` | `completed BOOLEAN DEFAULT false` |
| **日付のみ** | `DATE` | 時刻情報が不要な日付 | `YYYY-MM-DD` | `deadline DATE` |
| **日時** | `TIMESTAMP` | 日時情報が必要な場合。タイムゾーンなし | `YYYY-MM-DD HH:MM:SS` | `created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP` |
| **トークン** | `VARCHAR(64)` | 固定長のランダム文字列（UUID等を文字列化） | 64文字 | `token VARCHAR(64) UNIQUE` |

### データ型の補足

- **UUID**: PostgreSQLの`uuid`型を使用。Prismaでは`String`型として扱う
- **TIMESTAMP**: タイムゾーン情報は不要なため`TIMESTAMP`（`TIMESTAMPTZ`ではない）を使用
- **TEXT vs VARCHAR**: 長さ制限が明確な場合は`VARCHAR(n)`、可変長の場合は`TEXT`を使用
- **INTEGER**: 投票数や順序など、負の値が不要でも`INTEGER`を使用（将来の拡張性を考慮）

## 5. マイグレーション方針

### マイグレーションツール

**Prisma Migrate**（Prisma ORM使用時）

### マイグレーション手順

1. **スキーマファイル更新**
   - `prisma/schema.prisma` を編集
   - モデル定義、リレーション、制約を定義
2. **マイグレーション作成**
   ```bash
   npx prisma migrate dev --name {マイグレーション名}
   ```
   - 例: `npx prisma migrate dev --name add_vote_count_to_goals`
   - マイグレーションファイルが `prisma/migrations/` に生成される
3. **開発環境でテスト**
   - マイグレーションを適用して動作確認
   - ロールバックが必要な場合は手動で対応
4. **本番環境に適用**
   ```bash
   npx prisma migrate deploy
   ```
   - 本番環境では `migrate deploy` を使用（対話的プロンプトなし）

### マイグレーション命名規則

| パターン | 命名例 |
|----------|--------|
| **テーブル追加** | `create_users_table`, `create_teams_table` |
| **カラム追加** | `add_vote_count_to_smart_goals`, `add_icon_url_to_users` |
| **カラム削除** | `remove_old_column_from_table` |
| **カラム変更** | `change_status_type_in_smart_goals` |
| **制約追加** | `add_unique_constraint_to_team_members` |
| **インデックス追加** | `add_index_to_goals_team_id` |

### 注意事項

- **データ損失の可能性**: カラム削除や型変更時は、データ移行スクリプトを事前に準備
- **外部キー制約**: 参照整合性を保つため、外部キー制約を適切に設定
- **トランザクション**: マイグレーションは1つのトランザクションで実行される（失敗時はロールバック）
- **本番環境**: 本番環境への適用前に、必ずステージング環境でテスト

## 6. バージョン管理

### スキーマ定義の管理

- **定義ファイル**: `prisma/schema.prisma` で管理
- **バージョン管理**: Gitで管理（`schema.prisma` と `prisma/migrations/` ディレクトリ）
- **マイグレーション履歴**: `prisma/migrations/` ディレクトリに時系列で保存

### マイグレーションファイルの構造

```
prisma/
  ├── schema.prisma          # 現在のスキーマ定義
  └── migrations/
      ├── 20240201000000_init/
      │   └── migration.sql  # 初期スキーマ
      ├── 20240202000000_add_vote_count/
      │   └── migration.sql  # 投票数カラム追加
      └── ...
```

### バージョン管理のルール

1. **スキーマ変更は必ずマイグレーションで管理**
   - 直接SQLを実行せず、Prisma Migrateを使用
2. **マイグレーションファイルはGitにコミット**
   - チーム全体で同じスキーマを共有
3. **マイグレーション名は意味のある名前にする**
   - 後から変更内容が分かるように
4. **本番環境への適用は慎重に**
   - ステージング環境で十分にテストしてから適用

### スキーマのバージョン確認

```bash
# 現在のマイグレーション状態を確認
npx prisma migrate status

# スキーマとデータベースの差分を確認
npx prisma migrate diff
```

## 7. 補足事項

### データベース接続設定

- **接続文字列**: 環境変数で管理（`.env`ファイル）
  ```
  DATABASE_URL="postgresql://user:password@localhost:5432/saiteki?schema=public"
  ```
- **接続プール**: Prismaが自動で管理

### バックアップ方針

- **頻度**: 日次バックアップ（非機能要件定義書より）
- **方法**: PostgreSQLの標準バックアップツール（`pg_dump`）を使用
- **保持期間**: 30日間（要確認）

### セキュリティ考慮事項

- **パスワードハッシュ**: `password_hash`カラムに保存（平文は保存しない）
- **UUID使用**: 主キーにUUIDを使用することで、ID推測を困難にする
- **招待トークン**: `invitations.token`は推測不可能なランダム文字列（UUID等）を使用
